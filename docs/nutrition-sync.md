# Протокол синхронизации

Рабочие обработчики: POST `/sync/push`, GET `/sync/pull?since=CURSOR&limit=100`.
Старые пути `/v1/nutrition/sync/push|pull` оставлены как совместимые алиасы.
[Полная OpenAPI-схема](nutrition-openapi.json) генерируется из фактического приложения.
[Пример outbox Drift](nutrition-push.example.json) остаётся допустимым пакетом КБЖУ.

JWT определяет владельца и device. Входное тело не принимает userId.
Пакет содержит 1–100 разных сущностей и mutationId; DTO запрещают лишние поля.
Мутация: UUID mutationId/id, entity, operation upsert/delete, baseVersion >= 0,
clientRevision >= 1, data (null для удаления). Ответ: applied и cursor.

Идемпотентность: user+mutationId и user+device+entity+id+clientRevision.
Сервер запоминает SHA-256 канонического запроса и результат; изменение тела с прежним ключом
отклоняется. baseVersion должен совпадать с текущим serverVersion; иначе 409.
Весь push атомарен. Серверная транзакция блокирует пользователя до commit, поэтому курсор
более поздней операции не может обогнать незакоммиченный журнал ранней операции.

Pull возвращает изменения, nextCursor, hasMore, максимум 500 записей.
Курсор подписан HMAC и привязан к пользователю. Старт — since=0; неверный/чужой курсор — 410.
Журнал неизменяемый, tombstones не очищаются. Масштабируемое уплотнение истории потребует
отдельного протокола snapshot; текущая версия его не имитирует.
Push-cursor не используется клиентом как подтверждение pull.

Продукты хранят БЖУ/калории на 100 г, записи — неизменяемый снимок продукта.
Удаление продукта не удаляет историю. Удаление приёма пищи журналирует tombstone и
каскадные tombstones его записей. Составные FK и запросы репозиториев ограничены владельцем.
При совпадении дня/типа на двух устройствах 409 meal_alias сообщает canonicalId
и currentVersion только для своего пользователя; клиент атомарно переписывает локальные ссылки.

Сущности: product, meal, entry, profile, goal, workout, progress, achievement.
Общее описание клиента — [lib/core/sync/README.md](../lib/core/sync/README.md).
