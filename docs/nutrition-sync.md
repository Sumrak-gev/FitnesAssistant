# Протокол синхронизации питания

Контракт версии 1.0.0: [OpenAPI](nutrition-openapi.json),
[реальный пример сериализации из Drift/Dart](nutrition-push.example.json).
Типы: `lib/core/api/nutrition_contract.dart` и `server/app/nutrition_contracts.py`.
Схема генерируется командой `python -m app.export_nutrition_contract` из `server/`.
Эти HTTP-маршруты пока не подключены к FastAPI: контракт подготовлен для этапа
авторизации и синхронизации. Локальный дневник работает полностью без сети.

## Владение и идентификаторы

Сущности имеют UUID, создаваемый клиентом до отправки. Пользователь определяется
сервером по проверенному access-токену; тело запроса не принимает `userId`.
Все запросы репозитория ограничены владельцем. Составные внешние ключи записей
дополнительно запрещают связывать продукты и приёмы пищи разных пользователей.
Локальный `nutrition_users.id` — идентификатор локального владельца, а не токен
авторизации и не доказательство владения серверной учётной записью. Привязку
локального владельца к вошедшему аккаунту выполняет будущий слой авторизации.

Продукт хранит значения на 100 г. Приём пищи — календарная дата `YYYY-MM-DD` и
`breakfast | lunch | dinner | snack`; один слот каждого вида на пользователя и день.
Запись рациона ссылается на продукт и приём пищи и содержит граммы и снимок продукта.
Даты питания не преобразуются через UTC: при смене часового пояса дата остаётся
выбранной пользователем. Технические timestamps — UTC с часовым поясом.

## Push

`POST /v1/nutrition/sync/push`: пакет из 1–100 изменений. У каждого изменения:

- `mutationId`: UUID для идемпотентного повторения операции;
- `entity`: `product | meal | entry`, `id`: UUID сущности;
- `operation`: `upsert | delete`;
- `baseVersion`: известная клиенту серверная версия, 0 при создании;
- `clientRevision`: локальная ревизия, увеличиваемая при каждой правке;
- `data`: типизированные поля сущности для upsert, `null` для удаления.

Один пакет содержит не более одной операции для каждой сущности. Родители
передаются раньше записей. UUID продукта в snapshot должен совпадать с `productId`.
Снимок пищевой ценности передаётся явно, чтобы сохранить историю при офлайн-правках
каталога. Сервер проверяет значения и принадлежность ссылок владельцу. При изменении
массы/даты уже существующей записи с тем же продуктом сервер сохраняет её старый снимок.

Для будущего HTTP-обработчика зафиксирована следующая семантика:
пакет выполняется одной транзакцией; повторный `mutationId` с тем же содержимым
возвращает исходный результат, с другим содержимым отклоняется. Несовпадение
`baseVersion` даёт 409 и не перезаписывает чужую правку. При конфликте естественного
ключа приёма пищи `(user, day, kind)` клиент получает канонический UUID слота,
перепривязывает ожидающие записи и повторяет операцию. Обработчик должен хранить
серверный журнал изменений и квитанции идемпотентности в той же транзакции;
эти части транспортного слоя пока не реализованы.

Ответ содержит `applied` (mutationId, entity, id, version) и текущий `cursor`.
Клиент подтверждает только перечисленные mutationId; накопленные позже правки
сохраняются. Версия подтверждения обновляет `serverVersion`; последующие ожидающие
изменения этой сущности отправляются с новой baseVersion.

## Pull

`GET /v1/nutrition/sync/pull?cursor=...&limit=100`: серверные изменения текущего
пользователя, включая tombstones. `limit`: 1–500. Ответ: `changes`, `nextCursor`,
`hasMore`. Cursor непрозрачен и относится только к вошедшему пользователю;
пустой cursor означает начальную выгрузку. Его реализация должна исключать потери
при конкурентных коммитах: обычного фильтра `updated_at > timestamp` недостаточно.
Порядок на каждой странице детерминирован, граница страницы не теряет записи
с одинаковым временем. При истёкшем cursor ответ 410 требует полной сверки.

Для pull `version > 0`, `updatedAt`/`deletedAt` содержат timezone. Tombstone имеет
`deletedAt` и `data = null`. Версия определяет порядок конфликтов, часы устройства
не выбирают победителя. Удаления не стираются физически до подтверждения всеми
участвующими устройствами либо согласованного срока хранения с полной сверкой.

## Локальная очередь и ограничения

Каждая правка и соответствующая запись `nutrition_outbox` сохраняются одной
транзакцией Drift. `pendingMutations()` возвращает первые ожидающие операции,
не более одной на сущность. Это подготовка пакета; отправка, подтверждения,
перепривязка аккаунта, обработка конфликтов и применение pull ещё не подключены.
Без подтверждения очередь не очищается. Серверные репозитории вызываются внутри
транзакции вызывающего кода и сами не делают commit.

Удаление продукта не удаляет историю. Удаление приёма пищи создаёт tombstones
для него и всех его живых записей. Повторное использование слота приёма пищи
не восстанавливает старые записи. После подключения обработчиков синхронизации
серверный журнал должен включать также все каскадно изменённые записи.

Ошибки: 401 `unauthorized`, 409 `version_conflict`/`reference_missing`,
410 `cursor_expired`, 422 `validation_error`. Недоступные чужие UUID не раскрывают
данные другого пользователя. Передача персональных данных допускается только
после подключения авторизации и обновления политики конфиденциальности.
